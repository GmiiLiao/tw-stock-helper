## 0. 先講我會擋稿的三個前提（總編輯＋查核員的立場）

1. **LLM 不准自己打數字。** 這頁最大的風險不是文筆，是數字與日期寫錯、而且看起來很合理（本專案歷史上每一次嚴重事故都是「看起來合理的錯」）。設計上改成**數字槽位**：LLM 寫 `{{m.ew}}`，程式用資料包的值與固定格式填入；LLM 輸出裡出現未授權的裸數字＝擋稿。這讓「數字必須在資料包找得到」從事後比對變成事前不可能違反。
2. **推薦個股是這頁與熱力技能的邊界突破，必須由使用者明確裁定。** 熱力技能 §0／§5 與 2026-10-04 裁定是「只描述收盤事實、不預測、不計分、LLM 只准吃事實欄位」。現在要 AI 寫「明日預期」並列 5–10 檔個股，等於把描述層升格成「觀察名單」。本草案的做法是：措辭一律「觀察名單／資料整理」、機械查核擋住價格目標與買賣語、全部記錄只供事後對答案、不進任何模型分數——但**要不要做、叫不叫「推薦」、對誰公開**仍須使用者裁定（見 §4、決策清單 D1–D3）。
3. **昨日／今日／明日三張卡的「推薦」語意不同，要分開記錄。** 昨日、今日兩張是「已知結果後挑的回顧個股」，只有明日卡是事前觀察名單。若三張混在一起對答案，績效會被事後挑選灌水（本專案 2026-09-30 的「基準日不同批」教訓同類）。所以 schema 把 `kind` 分成 `recap`（回顧）與 `watch`（觀察），**只有 `watch` 進對答案統計**。

## 1. 整體產出結構

### 1.1 日期語意（先定義，否則三張卡會講不同的「今天」）

issue 以**資料日 D**（最後交易日，與 `dailyHeatmap/latest.dataDate` 同源）為鍵。三張卡的資料日：

| 卡 id | 標題（程式產生，非 LLM） | 資料日 | 內容性質 |
|---|---|---|---|
| `prev` | 昨日股市（前一交易日 M/D） | D 的前一交易日 D−1，取 `tradingDates` 清單，不用日曆減一 | 回顧：D−1 盤面事實、當日主因；picks `kind:'recap'` |
| `data` | 今日盤後（當日／前交易日 M/D） | D | 回顧：D 與 D−1 的差異、交易動能、權值股；picks `kind:'recap'` |
| `next` | 明日預期（下一交易日 M/D） | 下一交易日 N（`system/tradingCalendar`，非 D+1 日曆日） | 條件式觀察：影響 N 的全球與本土因素；picks `kind:'watch'` |

卡片標題上的「昨日／今日／明日」字樣在實際瀏覽時可能與日曆不符（例如週一早上看到的「昨日」是週五），所以**標題一律附 M/D 與站上既有 `dayLabel()` 規則**（資料日早於台北今天＝「前交易日」，等於今天＝「當日」）。這是否照使用者字面命名，列決策 D4。

### 1.2 Issue JSON schema（render-ready，也是第二大腦定版檔本體）

欄位命名遵守既有掃描規則：全部 key 不得符合 `/score|signal|buy|rank/i`（`compute.test.mjs:126`），本草案再加碼禁 `sell|target|stop|entry|exit|action|rating|rec(ommend)`。個股欄位叫 `focus`（關注個股），不叫 `picks`／`recommend`。不放任何數值型「信心」欄（會被讀成分數），只放封閉清單的等級標籤。

### 1.4 第二大腦存放（沿用 `second-brain/daily-heatmap/` 慣例）

```
second-brain/daily-analyst/
  {D}.json.gz                  # 定版 issue（上列 schema，payload 不含時間戳、鍵序固定）
  {D}.pack.json.gz             # 資料包（含 refs 表；任何人可用它＋issue 重跑 check.mjs 重驗）
  {D}.transcript.jsonl.gz      # 各輪原稿、R2 討論、查核 findings、退回與修補、被排除候選與原因（稽核用，不上 Firestore）
  reports/{D}.md               # 人讀 Markdown（render 與頁面共用函式）
  _manifest.json               # rows[D] = {status:'final', file, sha256, bytes, schemaVersion, canonicalAt, lateBuilt,
                               #            rebuilt:false, engineTier, packSha256, inputs:{…各輸入 echo＋sha256}, check:{…}, degraded:[…]}
  latest.json                  # {dataDate, canonicalAt, usableForNextDayBrief}
  _pending/{D}.json            # 資料未到齊或查核不過的原因
  _alerts/LATEST.json          # 過下一交易日 08:30 仍未定版（盤前簡報應顯示「昨日分析未產出」）
  _review/{D}.json             # 事後對答案，由獨立程式寫（§1.5），與 issue 檔分開
  .lock
```

沿用的規則（直接抄 `daily-heatmap.mjs` 的 `writeOnce`）：atomic 寫（tmp＋rename）、`.lock`（`wx`）、**寫一次**；開盤前 `--force` 修補舊檔改名 `.r{n}`、開盤後只寫 `.amend-{n}`、不取代原檔；manifest 記每份輸入的 sha256；非交易日不產檔。
**確定性的誠實說明**：熱力是同輸入同輸出；LLM 產出不可重現。這裡的「確定性」降級為**可稽核**：同一份 issue＋pack 重跑 `check.mjs` 必得同一個查核結果，且 pack 與每輪原稿都留檔、`promptSha256`／模型 id 記進 meta（`wm-llm-provider-routing`：「判定結果落地要標 provider/model 版本」）。

**發佈到 Firestore**：`dailyAnalyst/latest` ＋ `dailyAnalyst/{D}`（去掉 transcript／pack；估 60–120 KB，`publish-daily-heatmap.mjs` 同樣做 900 KB 守門；API 回應走 `gzipJsonAuto`）。同一份定版（canonicalAt 相同）不重寫、不讓舊資料日蓋掉新的 latest（照抄 publish-daily-heatmap）。Firestore 禁巢狀陣列：FocusStock 內 `evidence/risks` 是物件陣列，沒問題；pack 不上雲。

**登記清單（缺一等於沒保護，CLAUDE.md 與 backup-brain 檔頭都寫明）**

### 1.5 事後對答案（只記錄，不得進模型分數）

- **獨立程式** `scripts/verify-daily-analyst.mjs`（仿 `verify-daily-heatmap.mjs`），在資料日 +1／+5 個交易日**收盤歸檔到齊後**才跑（用 `canonical-gate` 的 `archiveCloseReady`），寫 `second-brain/daily-analyst/_review/{D}.json`。**不寫 Firestore、不寫 picksHistory／picksScoreboard**；不被任何 daemon 讀取（加一條 import 掃描測試，與熱力 `usedForScoring` 測試同型）。
- 只評 `kind:'watch'`（明日卡）。`reviewSpec` 在 issue 定版時就寫死（refBasis＝資料日收盤；horizons＝1、5 個交易日），事後不得換口徑。報酬一律用官方參考價日報酬連乘（熱力技能 §0-2：不可用 `chipArchive.closeJson` 算日報酬，除權息日會錯），**未扣成本**，**基準＝同一批日子的同日等權 `market.ew`**（CLAUDE.md「基準取同一批進場日」）。
- **命中與漏網兩份記錄**（記憶：feedback_backtest_hits_and_misses）：命中表逐檔列分析師提名、證據 refs、結果；漏網表列 D+1 `board.gainers` 前 N 檔未入名單者，附「在池內？被排除原因？有無相關消息」供迭代查原因。
- `recap` 卡的個股只記錄，不統計績效；統計頁面（若將來做）必須標「事後挑選，不代表可交易績效」。
- 樣本期限制照實寫：至少累積 ≥20 個交易日才能看任何彙總；之前只顯示逐日，不顯示命中率（避免小樣本誤導）。

### 2.2 資料包內容與時點隔離

資料包是**唯一事實來源**，三位分析師與總編輯都只看 pack，不上網、不讀 repo、不讀 Firestore。

- `refs`：扁平表 `id → {v, unit, fmt, asOf, tier, source}`，約 300–500 筆（估 8–12k tokens；未驗，需實測；Ollama 路線尚須確認 daemon 的 `num_ctx`，daemon 刻意不覆寫以免模型重載）。
- 命名空間：`m.*` 市場；`ix.*` 指數與權值股貢獻；`br.*` 廣度；`ind.{產業}.*` 官方產業別；`st.{code}.*` 候選個股事實（ret、valM、close、flags、industry）；`nv.{code}.*` 媒體判別（M，含 label／eventType／certainty／priced／reason，**內文不放**，只放判別結果與標題）；`mo.{id}.*` 官方公告（O，主旨、類型、規則方向）；`gl.{sym}.*` 全球；`fx.*`／`adr.*`；`cal.*` 行事曆（除權息、法說）；`wk.{code}.*` wiki（強制帶 `tier:'AI待驗'|'站內整理'|'官方衍生'`）；`prev.*`／`diff.*` D−1 值與 **程式預先算好的差值**（分析師不做算術）。
- **時點隔離**：`prev` 卡的 claims／focus 只能引用 `asOf ≤ D−1` 的 refs；`data` 卡 `asOf ≤ D`；`next` 卡可引用全部，但**不得引用任何 N 日（下一交易日）的資料**（防偷看，同「事前存檔」邏輯；pack 本來就不含）。checker R17 機械驗證。
- **官方 O 與媒體 M 分兩個子樹，pack 不提供任何兩者合計欄位**（對齊 tw-daily-heatmap §6 與 tw-news-impact-analyst §2）。
- 熱力 `watch.continue/catchup/risk`：放進 pack 時 `tier:'先驗·未驗證'`，只能當「待觀察假說」引用、不得單獨當 focus 的證據（SKILL §3／§5：證據為先驗，2022–2023 無效）。熱力技能禁止「餵 LLM 當方向依據」——**這條要由使用者確認：分析師引用熱力事實欄位並下「方向詞」是否算違規**（決策 D6；我的設計是：事實欄位可吃，`watch` 與 `layers` 只能以「先驗·未驗證」標籤當背景）。

| 角色 | 讀的 pack 子樹 | 負責 |
|---|---|---|
| 盤面動能分析師 `momentum` | `m/ix/br/ind/diff/prev`、`st`（成交與漲跌）、籌碼（若 P3 過） | 今日大盤結果；與上一交易日有何不同；交易動能怎麼進行（權值股 vs 一般、族群輪動、量能、漲跌停） |

| 全球與總經分析師 `global` | `gl/fx/adr`、`cal`（全球事件若有）、`m` 摘要 | 隔夜與全球環境；匯率、商品、ADR 溢價；對台股的傳導路徑（只提「路徑」，不提「必然」） |

**輪次（建議 3 輪＋查核，總呼叫 8–12 次）**

| 輪 | 輸入 | 輸出 | 誰擋 |
|---|---|---|---|
| R0 資料包（程式） | 各來源 | `pack.json`、sha256、`absent`、候選池（含排除原因） | 閘門 P1–P8 |
| R1 獨立撰稿（3 路平行，彼此看不到） | 各自的 pack 子樹＋該卡候選池 | 每人 `draft`：`claims[]`（三卡各自段落）＋`focusProposals[]`（每卡每人最多提 6 檔、附 evidence/risks/watchConditions） | 機械查核 v1 逐稿跑：不過就把 `findings` 退回該分析師自我修補，**最多 2 次**，仍不過則該稿裁掉違規 claim（不是整稿作廢） |
| R2 交叉審閱（3 路平行） | 另兩位的 `claims`＋`focusProposals`（**只給結構化內容，不給散文**）＋pack 全部 refs 索引 | 每人 `crossNotes`：同意／反對／缺漏（各 ≤5 條，每條帶 ref）；共同署名的 `linkages[]`（from 與 to 必須分屬兩位分析師的領域，例如 global 的 `gl.^SOX` → industry 的半導體族群消息）；對他人提名個股的**否決理由**（若有） | 機械查核：linkage 的 mechanism 必在封閉清單、tier ≤ 站內整理 |
| R3 總編輯整合（單呼叫） | 通過查核的三份 draft＋crossNotes＋pack 摘要 | 三卡與總結卡成稿：去重、統一口徑（同一數字同一格式、同一方向詞）、挑 focus（§3.3 的名額規則）、寫 `headline`／`nextFocus`／`risks`；**不得新增 pack 以外的事實** | 機械查核 v2（整頁） |
| R4 查核員（機械＋LLM 紅隊） | 成稿＋pack | 機械：§3 全部規則。LLM 紅隊（獨立提示詞、**不給分析師的推理，只給成稿＋pack**）：逐 claim 判「pack 是否支持」「是否有暗示買賣」「是否與同頁其他 claim 矛盾」「是否把傳聞當事實」 | 擋稿／退回：`blocker` 退給總編輯修（≤2 輪）；`redaction` 類由程式刪該 claim／該檔（不重打 LLM）；2 輪後仍有 blocker ＝降級（§2.5） |

討論的實質（避免「三個人格同一模型自說自話」）：
- R1 資訊隔離（各看各的子樹），R2 才交換——這是唯一能產生「不同意」的結構設計；
- R2 輸出強制 `cross-refs`（必須引用他人的 claim id），使「連動分析」有可驗證的兩端；
- 提名制：每檔 focus 至少 1 位分析師提名；被他人以 ref 為據否決者，總編輯必須在 transcript 記錄處置理由；
- 總編輯一致性清單（程式輔助）：同一個 ref 在全頁數值格式一致；同一檔個股在三卡的描述不矛盾；日期標示一致；總結卡不引入新 ref。

## 3. 機械查核規則（可寫成程式與測試）

實作：`scripts/lib/daily-analyst/check.mjs` 純函式 `checkIssue(issue, pack) → { pass, blockers[], redactions[], warnings[] }`；`check.test.mjs` 每條規則至少 1 正例＋1 反例；另跑「既有模板輸出零誤殺」回歸（拿 `narrative.mjs` 的輸出與歷史 `reports/*.md` 當負樣本集，禁用詞表的誤報要降到 0 才算上線）。

### 3.1 證據引用語法

- **值槽位** `{{ref|fmt}}`：程式依 `pack.refs[ref]` 填值並套固定格式；`fmt` 為封閉清單：`sg2`（帶號兩位小數）、`int`（千分位）、`pts1`、`bn1`（億元一位）、`pct0`、`date`。LLM 不得自行輸入該數字。
- **引用標記** `[ref:id]`（句末，可多個）：宣告該句依據但不填值，用於 `thesis`、`watchConditions` 等本來不含數字的句子。claim 的 `refs[]` 欄位是兩者的聯集（由程式從文字抽出再與 LLM 宣告比對，不一致即 blocker）。
- id 文法：`^[a-z]{1,3}(\.[A-Za-z0-9^=_\-]+){1,4}$`，必須存在於 `pack.refs`。個股 `st.{code}.*` 的 `{code}` 必須等於該 FocusStock 的 `code`（防張冠李戴）。
- 渲染：前端點證據晶片可看 `ref → 值、資料日、來源、等級`（pack 的精簡版 `refTable` 隨 issue 發佈，只含被引用到的 refs，約數十 KB 以內）。

### 3.2 規則表（Block＝擋稿退回；Redact＝程式刪除該 claim／該檔；Warn＝記錄）

| 編號 | 規則 | 實作要點 | 級別 |
|---|---|---|---|
| R01 | schema 合法：欄位齊全、型別、封閉清單（kind/tier/direction/mechanism/role）、長度上限、key 不符 `/score|signal|buy|sell|rank|target|stop|entry|exit|action|rating/i` | JSON schema＋走訪鍵名（沿用 `compute.test.mjs:126` 手法） | Block |
| R02 | `usedForScoring===false`、`disclaimer`／`disclaimerShort` 與程式常數**逐字相等**、`useRules.forbidden` 未被改 | 程式寫入，LLM 欄位不收；比對 sha | Block |
| R03 | 數字授權：文字中所有數值字面量，必須來自 `{{}}` 槽位，或屬白名單（日期、股票代號、`5–10` 這類結構性數字、條列序號、「前 N 大」的 N 且 N 與列出筆數一致）。其餘裸數字一律擋；若將來放寬為允許裸數字，容許規則＝與同句引用 refs 之一的值在**使用者打出的小數位**四捨五入後相等，且單位換算（億／萬／%）一致 | 正規式抽數字＋白名單；單測含 `0.57` vs `0.6`、`1,144,137` vs `1144137` | Block |
| R04 | 所有 refs 存在於 pack；`ref.asOf` 不晚於該卡資料日（時點隔離，§2.2） | 查表＋日期比較 | Block |

### 3.3 候選池與名額（把「選哪幾檔」降到可驗證）

- 池由程式產生，**LLM 不能自己加股票**。每卡一個池，規則版本號 `pool-v1`，寫進 issue 與 manifest：
  - `prev`：D−1 熱力 `board`（漲幅居前、成交值居前、權值股拉抬／拖累）＋ D−1 當日 O 公告重大者；
  - `data`：D 同上＋ D 的 `nv` 媒體判別前 N（M 管線）＋ D 的籌碼；
  - `next`：D 的上述聯集＋ N 日 `cal.*` 事件（除權息、法說）＋隔夜 O 公告＋ `nv`（適用日 N）；
  - 一律先套 R15 的排除；排除清單與原因進 transcript（對答案時查「漏網」用）。
- 名額流程（總編輯，程式輔助）：先收各分析師提名→去除被否決→每檔補 `adverse[]`→依「提名人數、證據是否含官方、是否與其他卡重複」做**確定性排序顯示用的規則**（不命名為 score/rank，也不寫進分數；排序鍵值不輸出）→取 5–10。**這個排序只決定版面順序，不代表強弱。**
- 池大小、成交值門檻、新上市天數需實測校準（我不亂給數字；`1 億`只是暫訂，標為待量測）。

### 4.2 站上既有「推薦」免責寫法（grep 結果摘要）

- 通用：「確定性統計，非投資建議」（ChipDualCard／FinHealth／ChipWind）、「僅供參考，非投資建議」（AiNewsTicker）、「模擬交易，非投資建議；過去的模擬成績不代表未來」（MyAiLab／AiLabTargets）。
- 研究／榜單：「研究模型名單，不取代站上漲停預測、不構成推薦；未扣成本；非投資建議」（SurgeShadow）、「研究回測數字：未扣成本；非投資建議」（`LAB_FOOT`）；`SignalPanel`：「以上為技術分析建議，非投資建議。實際操作請結合個人風險承受能力」；ChipPicksPanel／LimitUpPanel 有「追高風險極大」「分級/勝率為回測估計，非即時保證」「進場鐵律：單筆風險≤1%」等較強的操作語氣——**這類語氣（進場、停損試算）本頁一律不用**（R09）。
- help-content.ts：只有「資料為準、非投資建議」「樣本少於 30 次的勝率僅供參考」兩處，沒有統一免責長文。
- 結論：站上現行是**短句式、各元件自帶**，沒有單一常數。建議這頁起就建一個 `DISCLAIMER` 常數（程式碼層單一來源），本頁使用，其他頁日後逐步改用。

### 4.3 法律風險（我不是律師，只標出需要使用者確認的點）

「對不特定公眾（尤其收費會員）列示個股並附理由」在台灣可能接近證券投資顧問業務的界線（證券投資信託及顧問法對「就有價證券之價值、買賣之判斷提供分析意見或推薦建議」並收取報酬的行為有許可規定）。這是**本設計最大的非技術風險**。降低風險的設計選擇（皆不構成法律結論）：
- 名稱用「資料觀察名單／焦點個股」，不用「推薦」「買進」「強力」「精選」；
- 不含價格目標、停損、進出場、部位或資金建議（R09）；
- 理由限定為「已發生的事實與可觀測的條件」，不寫報酬預期；
- 若限定會員：付費牆後的個股清單更像「收費建議」，反而風險更高——見 D2；
- 建議上線前請使用者自行諮詢合格專業人士；此為決策 D1 的前提。

### 4.4 建議的免責聲明文字（zh-TW，程式常數）

**長版（頁首與 issue 檔內）**
> 本頁由 AI 分析師依證交所、櫃買中心、公開資訊觀測站等官方資料與站內整理資料撰寫，經程式查核數字與引用來源。內容為資料日的市場事實描述與條件式觀察，**不是投資建議**，不含價格目標、買賣或進出場指示，也不保證任何結果。列示的個股僅為資料整理出的觀察名單，不構成推薦、招攬或個人化投資建議。AI 可能出錯，請以官方公告為準；報酬數字未扣交易成本，過去的表現不代表未來。投資請自行判斷並承擔風險。

**短版（每張卡底部，R25）**
> AI 整理，非投資建議；個股為資料觀察名單，非買賣建議。

另：媒體 M／官方 O 的區別、傳聞、AI待驗等標示用 tier 標記自動帶出（R14），不寫進免責。

### 4.5 公開 vs 會員限定（參考 `access.ts`／`view-as.ts`／`require-premium.ts` 現況）

現況：`🌙 盤後報告` 目前**公開**（Dashboard DASH_TABS，無 premium 過濾；`/api/twse/daily-heatmap` 與 `after-market-news` 為公開 CDN 快取 API）。站上付費牆做法：導覽層 `NAV_ITEMS[].premium`＋`useIsPremium()`（有效等級，含身分模擬）＋體驗期 14 天（`access.ts`／Navbar `trialActive`），**API 層**用 `requirePremium(request)`（verifyIdToken＋2 分鐘 uid 等級快取；strategy-picks、my-ai-lab 在用）。注意 `useIsPremium` 本身**不含體驗期**，Navbar 另外自己算 `trialActive`，要做頁面級 gating 須兩者併用（既有不一致，非本案範圍，但別漏）。

我的建議（供 D2 裁定）：
- **分析文字（總結卡＋三卡的 claims＋連動）公開**：它們是已發生的市場事實描述，與現行公開的盤後報告同性質，可吃 CDN（`daily` tier）。
- **個股觀察名單（`focus.stocks`）預設不公開付費牆**，兩個方案：
  - (甲) 全公開，法律風險集中在措辭（4.3）；
  - (乙) 會員限定＋體驗期：走獨立 API `GET /api/twse/daily-analyst/focus`＋`requirePremium`，回應 `cacheHeader('private')`，伺服器端用 `memoize` 合流讀 Firestore（讀取次數與人數脫鉤）。**但 4.3 指出收費牆後更像收費建議**，所以若使用者想謹慎，我反而傾向：**研究期（≥20 個交易日對答案前）觀察名單只給管理員／超級管理員後台看，不對一般使用者公開**（與「研究期不計分」「研究模型名單不構成推薦」現有做法一致，SurgeShadow 即是此模式）。
- 不論哪案，Firestore 規則維持 server-only 讀取（現有 dailyHeatmap 無 client 規則，走 admin SDK）。

- 使用既有 `Card`（`shared.tsx`，標題列可收合、有 `dataDate`／`dateLabel`／`tier` 標籤）；桌機兩欄（左：分析段落、右：關注個股）、手機單欄堆疊；每卡 `dateLabel` 用 `dayLabel(資料日)`。
- 證據晶片：句末小標籤（如 `官方`／`媒體`／`AI待驗`／`傳聞`），點開以 `Detail` 區塊列出 ref 值、資料日、來源（資料來自 issue 內的 `refTable`），符合「每個數字都標註日期」。
- 同一檔個股在多卡出現時，加小標示「亦見於 今日盤後」。

### 5.3 個股列（沿用 `StockCell`／`PriceCell`）

每列：`StockCell`（市／櫃圖示＋代號名稱可點進個股分析＋`RiskBadge` 注意／處置標記）｜`PriceCell`（現價、昨收、漲跌%，**即時**）｜靜態「資料日收」（`前交易日 10/02 收 xx.xx`，用 issue 的 `asOf.closeRef`，與即時價分欄，避免混淆）｜一句理由 `thesis`｜證據晶片｜`watchConditions`（`next` 卡）｜`risks`（預設收合，點開；但**有 `adverse` 的列在列尾固定顯示「有反向資料」小字**，不可被收合隱藏——這是描述性標示不是警示色）。
`PriceCell` 的「現價＝即時價（盤中）／收盤價（收盤後）、昨收＝前一交易日收盤」規則照舊（`PriceCell` 已內建 title 說明）；文字段落**不內嵌即時價**（沿用現行 AnalysisReport 的說明「現價與昨收為即時資料，不在報告內」）。
注意：`StockCell` 的 `RiskBadge` 顯示的是**當下**風險旗標，若某檔在 issue 發出後才被列處置，列上會即時出現標記——這是既有全站行為，不算新警示；但該檔在 issue 內仍「合規入池」，兩者的時間差要在 tooltip 說明（資料日 vs 現在）。

## 6. 風險與未驗清單（誠實標示）

1. 所有 token／成本／延遲數字是**估算**，未實測。
2. gemma4 在多角色長 context＋槽位語法下的遵守率**未驗**；Ollama 的 `num_ctx` 是否容得下 pack（約 10k tokens）**未驗**。
3. `check-source-registry` 是否因新增雲端 LLM 呼叫而擋 commit **未驗**。
4. `riskStocks` 風險旗標的**歷史**可得性：熱力技能 §7 記鏡像只有 2026-10-02 一天；`prev` 卡（D−1）的排除判斷可能拿不到 D−1 當日旗標 → 依 P8「無法驗證即不入池」，`prev` 卡可能經常不足 5 檔，需使用者接受「不足就少列」（D9）。
5. 禁用詞表的誤殺率要靠回歸測試調；初版詞表偏保守。
6. 「新上市」「無量鎖死」的量化門檻需資料量測，未訂。
7. 法律風險（4.3）未經專業確認。
8. 美股收盤時刻（夏令／冬令）判定需用 America/New_York 時區計算，避免寫死 04:00／05:00。
